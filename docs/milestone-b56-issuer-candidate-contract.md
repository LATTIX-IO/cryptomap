# FOSS-483 — B5.6 bounded X.509 issuer-candidate correlation contract

Status: implementation contract; **not an accepted implementation**. Baseline:
protected `cryptomap/main` at `88cbd2d7fab9d1965d7f6480e1079ca9520fc2e6`, with B5.5 and separate Windows
adapter provenance signed and verified. The B5.6 changes must remain on the
FOSS-483 branch until the complete issue acceptance is satisfied.

## Security and semantic invariants

1. Inputs are **authorized, actually collected** certificate observations. An
   imported/re-hashed `InventorySnapshot` is not cryptographic proof that its
   `certificate:identity-*` properties were generated by B5.5. A live candidate
   builder must cross the same host-owned B5.5 raw-record HMAC receipt verification
   boundary used by `normalize_with_identity`. Multi-run reconciliation must
   verify original authenticated evidence and host-pinned scope separately;
   `verify_for_scope` alone is not a signed witness.
2. Correlation is constrained by a single collection-scope identifier,
   tenant/key-version namespace, and host-owned capability. Do not join across
   scopes, tenant keys, key versions, or rotations, even if opaque values happen
   to compare equal. Missing capability or unsupported ASN.1 DN comparison
   yields explicitly **NotInspected/Unknown**, not a verified empty graph.
3. Compare only role-neutral B5.5 issuer-DN and subject-DN HMAC tokens with
   exact namespace equality. A serial token is separately issuer-scoped and
   must not be used as a global join key. Public X.509 metadata is contextual
   evidence, not a cryptographic signature/path proof. No silent root-store,
   trust-anchor, AIA, AKI/SKI, revocation, or external CA lookup.
4. Candidate edges use **only** canonical `RelationshipKind::RelatedTo`
   (leaf certificate -> possible issuing certificate). Each edge has a
   deterministic, immutable `RelationshipId::from_endpoints` and supporting
   evidence explicitly marked `EvidenceKind::Inferred` with inference rule
   `x509:issuer-candidate:v1`. Preserve direct source evidence for both
   candidate endpoints; a direct record is **not** direct proof of issuance.
   Never emit `IssuedBy` or `ValidatedBy` from DN or serial equality.
5. Preserve existing v2 snapshot structure, frozen certificate AssetIds,
   existing source-run EvidenceIds, and existing relationship wire
   discriminants. An invasive schema extension requires its own compatibility
   ADR and golden migration corpus, not an unreviewed B5.6 side effect.
6. Self-issued is **not** self-signed: suppress self-edges without asserting
   trust. Ambiguous equal-subject candidates remain distinguishable possible
   candidates (subject to limits); avoid directed cycles and avoid producing
   evidence that implies chain/path validation. Do not merge distinct
   fingerprints simply because DN pseudonyms agree.
7. Strictly bound input certificate records, index memory, issuer fan-out,
   pair comparisons, emitted edges/evidence and graph traversal depth.
   Apply `RawLimits` and `InventoryLimits` in addition to local
   `CandidateLimits`. Budget exhaustion must yield typed **Partial /
   resource-limited** coverage and must not silently truncate a graph that
   claims completeness. Cancellation/failed/partial sources cannot be
   rewritten as clean/negative evidence.
8. No raw DN, SAN, serial, SKI, AKI, SPKI/public key bytes, certificate DER,
   private keys, tenant secrets or plaintext comparison material may be
   embedded in candidate edge metadata, diagnostics, logs, examples or
   redacted reports. Key-derived tokens remain pseudonymous and can leak
   equality information to authorized readers.

## Implementation sequence within the one FOSS-483 PR

- **A. Trusted inputs:** introduce a bounded adapter from already-validated
  B5.5 raw receipts and host-authorized collection runs to canonical
  certificate AssetIds and direct EvidenceIds. Reject imported pseudonym
  shapes without receipt verification. Keep the opt-in feature disabled by
  default and preserve ordinary pipeline snapshots without the capability.
- **B. Deterministic index:** build an ordered
  `(exact-namespace, subject-dn-token) -> [certificate asset, provenance]`
  index. Match exact issuer token, exclude identical asset identity, retain
  ambiguous alternatives, deduplicate duplicate file/store evidence, enforce
  per-token fan-out and pair ceilings.
- **C. Inferred graph:** synthesize namespaced inferred evidence plus
  `RelatedTo` edges, using canonical direction-aware IDs, sorted insertion,
  cycle/depth checks and a hard edge budget; annotate unknown/partial coverage.
  Never invent a verified relationship kind.
- **D. Batch/scope:** extend the same authenticated, bounded matching across
  explicitly authorized file/DER and granted Windows-store collection runs
  without importing unrelated tenant/context data or adding ambient discovery.
- **E. Acceptance:** prove stable IDs/bytes and source provenance for root,
  intermediate, leaf, unrelated, ambiguous same-DN, self-issued, duplicate
  PEM/DER/store and same serial/different issuer cases. Add invalid HMAC,
  scope/key-version mismatch, unsupported Unicode, expired-but-parseable
  public cert, malformed DER, forged snapshot, cancellation, partial failure,
  fan-out exhaustion, cycle and confidential-data leakage regressions.
  Execute exact-head Linux/Windows/Rust 1.85, Clippy -D warnings, docs,
  RustSec, Cargo deny, packaging/SPDX and independent review before merge.
  Verify signed protected-main provenance afterward.

## Exclusions and follow-up

Offline signature verification, explicit trust anchors, path constraints,
revocation at validation time, certificate compliance scoring, and the
remaining RustCrypto HMAC process-memory erasure research (FOSS-506) are
**separate** workstreams. This implementation establishes deterministic,
bounded issuer *candidates*, never verified PKI chains or trust decisions.
