# FOSS-483 — B5.6 bounded X.509 issuer-candidate correlation contract

Status: B5.6 implementation and acceptance contract for PR #71, based on
protected `cryptomap/main` at `88cbd2d7fab9d1965d7f6480e1079ca9520fc2e6`.
B5.5 and the separate Windows adapter have verified protected-main provenance.
B5.6 is not production-attested until its own merge and main-only signature checks.

## Security and semantic invariants

1. Inputs are **authorized, actually collected** certificate observations. An
   imported/re-hashed `InventorySnapshot` is not cryptographic proof that its
   `certificate:identity-*` properties were generated by B5.5. A live candidate
   builder must cross the same host-owned B5.5 raw-record HMAC receipt verification
   boundary used by `normalize_with_identity`. Multi-run reconciliation must
   verify original authenticated evidence and host-pinned scope separately;
   `verify_for_scope` alone is not a signed witness.
2. Correlation is constrained by a single collection-scope identifier,
   tenant/key-version namespace, and host-owned capability. Do not join across
   scopes, tenant keys, key versions, or rotations, even if opaque values happen
   to compare equal. Missing capability or unsupported ASN.1 DN comparison
   yields explicitly **NotInspected/Unknown**, not a verified empty graph.
3. Compare only role-neutral B5.5 issuer-DN and subject-DN HMAC tokens with
   exact namespace equality. A serial token is separately issuer-scoped and
   must not be used as a global join key. Public X.509 metadata is contextual
   evidence, not a cryptographic signature/path proof. No silent root-store,
   trust-anchor, AIA, AKI/SKI, revocation, or external CA lookup.
4. Candidate edges use **only** canonical `RelationshipKind::RelatedTo`
   (leaf certificate -> possible issuing certificate). Each edge has a
   deterministic, immutable `RelationshipId::from_endpoints` and supporting
   evidence explicitly marked `EvidenceKind::Inferred` with inference rule
   `x509:issuer-candidate:v1`. Preserve direct source evidence for both
   candidate endpoints; a direct record is **not** direct proof of issuance.
   Never emit `IssuedBy` or `ValidatedBy` from DN or serial equality.
5. Preserve existing v2 snapshot structure, frozen certificate AssetIds,
   existing source-run EvidenceIds, and existing relationship wire
   discriminants. An invasive schema extension requires its own compatibility
   ADR and golden migration corpus, not an unreviewed B5.6 side effect.
6. Self-issued is **not** self-signed: suppress self-edges without asserting
   trust. Ambiguous equal-subject candidates remain distinguishable possible
   candidates (subject to limits); avoid directed cycles and avoid producing
   evidence that implies chain/path validation. Do not merge distinct
   fingerprints simply because DN pseudonyms agree.
7. Strictly bound input certificate records, index memory, issuer fan-out,
   pair comparisons, emitted edges/evidence and graph traversal depth.
   Apply `RawLimits` and `InventoryLimits` in addition to local
   `CandidateLimits`. Budget exhaustion must yield typed **Partial /
   resource-limited** coverage and must not silently truncate a graph that
   claims completeness. Cancellation/failed/partial sources cannot be
   rewritten as clean/negative evidence.
8. No raw DN, SAN, serial, SKI, AKI, SPKI/public key bytes, certificate DER,
   private keys, tenant secrets or plaintext comparison material may be
   embedded in candidate edge metadata, diagnostics, logs, examples or
   redacted reports. Key-derived tokens remain pseudonymous and can leak
   equality information to authorized readers.

## Implementation sequence within the one FOSS-483 PR

- **A. Trusted inputs:** introduce a bounded adapter from already-validated
  B5.5 raw receipts and host-authorized collection runs to canonical
  certificate AssetIds and direct EvidenceIds. Reject imported pseudonym
  shapes without receipt verification. Keep the opt-in feature disabled by
  default and preserve ordinary pipeline snapshots without the capability.
- **B. Deterministic index:** build an ordered
  `(exact-namespace, subject-dn-token) -> [certificate asset, provenance]`
  index. Match exact issuer token, exclude identical asset identity, retain
  ambiguous alternatives, deduplicate duplicate file/store evidence, enforce
  per-token fan-out and pair ceilings.
- **C. Inferred graph:** synthesize namespaced inferred evidence plus
  `RelatedTo` edges, using canonical direction-aware IDs, sorted insertion,
  cycle/depth checks and a hard edge budget; annotate unknown/partial coverage.
  Never invent a verified relationship kind.
- **D. Batch/scope:** extend the same authenticated, bounded matching across
  explicitly authorized file/DER and granted Windows-store collection runs
  without importing unrelated tenant/context data or adding ambient discovery.
- **E. Acceptance:** prove stable IDs/bytes and source provenance for root,
  intermediate, leaf, unrelated, ambiguous same-DN, self-issued, duplicate
  PEM/DER/store and same serial/different issuer cases. Add invalid HMAC,
  scope/key-version mismatch, unsupported Unicode, expired-but-parseable
  public cert, malformed DER, forged snapshot, cancellation, partial failure,
  fan-out exhaustion, cycle and confidential-data leakage regressions.
  Execute exact-head Linux/Windows/Rust 1.85, Clippy -D warnings, docs,
  RustSec, Cargo deny, packaging/SPDX and independent review before merge.
  Verify signed protected-main provenance afterward.

## Exclusions and follow-up

Offline signature verification, explicit trust anchors, path constraints,
revocation at validation time, certificate compliance scoring, and the
remaining RustCrypto HMAC process-memory erasure research (FOSS-506) are
**separate** workstreams. This implementation establishes deterministic,
bounded issuer *candidates*, never verified PKI chains or trust decisions.


## Increment A — same-run bounded matcher implementation

The current branch implements a private, opt-in `issuer_candidates` stage in
`normalize_with_identity` after the existing source, run, host-window and
B5.5 HMAC receipt validation. It indexes unique certificate AssetIds by
role-neutral pseudonymous subject DN, matches authenticated issuer DN, emits
`RelatedTo` with a separate low-confidence inferred Evidence record named
`x509:issuer-candidate:v1`, and retains both endpoints' direct EvidenceIds.

The matcher has fixed ceilings (1,024 certificate assets/records, 32 candidates
per issuer token, 8,192 pairs, 1,024 edges, traversal depth 16) additionally
clamped to the invoking RawLimits and InventoryLimits. Exceeding a ceiling,
encountering unsupported pseudonyms, or skipping a candidate cycle yields
`CoverageState::Partial` under a separate namespaced candidate-coverage key;
it never upgrades the real collection coverage. Identical certificate assets
deduplicate; repeated source observations remain traceable. Invalid receipts,
malformed opaque tokens or conflicting hints for the same asset fail closed.

Increment A covers one authorized collection run; Increment B below extends
matching across independently authorized PEM/DER and memory-only certificate-store
runs while preserving exact source evidence and one common host-owned authority.
The B5.5 identity profile contains role-neutral issuer/subject DN hints and an
issuer-scoped serial hint, but **does not expose AKI/SKI comparison hints**.
AKI/SKI-based narrowing is optional future work requiring a separately reviewed
and versioned keyed-hint contract. Its absence does not imply X.509 verification.


## Operator verification for Increment A

Run against the FOSS-483 branch with all certificate-related features enabled:

    cargo fmt --all -- --check
    cargo clippy --workspace --all-targets --all-features --locked -- -D warnings
    cargo test -p cryptomap --all-features --locked issuer_candidates
    cargo test -p cryptomap --all-features --locked --test foss_483_issuer_candidates

The live integration regression uses two public DER certificates supplied by a
memory-only store provider. Its leaf TBS issuer DN matches a collected
certificate's subject DN, but the leaf is deliberately not re-signed after the
edit. Success therefore means **one candidate `RelatedTo` edge** with inferred
evidence—not cryptographic issuance or certificate validation. The test also
rejects an incorrect HMAC authority, an unauthenticated default normalization,
and a forged imported store-source reference.

Inspect `InventorySnapshot.relationships` for `RelatedTo`, resolve each
`Relationship.evidence` ID, and require an `EvidenceKind::Inferred` entry with
`inference_rule == "x509:issuer-candidate:v1"`. The direct evidence attached to
both endpoints remains independently traceable. Inspect the distinct
`x509:issuer-candidate:v1:<run-id>` coverage entry and treat `Partial` as
incomplete, *never* as a negative/trust conclusion. Do not interpret a missing
candidate relationship as proof that no issuer exists.

Use host-supplied CSPRNG-generated HMAC keys, exact source grants and the
existing `normalize_with_identity` interface. The matcher does not acquire
any system certificate-store permissions itself. Integration tests must not
read an actual Windows user or machine certificate store.


## Increment B — authenticated PEM/DER/store batch federation

The implementation adds two explicit entry points, both behind the existing
`certificate-identity` feature:

- `batch::normalize_batch_with_identity(runs, limits, authority)`: consumes
  independently collected `BatchRun` values with their host-pinned per-run
  scope/descriptor/source grants and one shared authority. It normalizes every
  run with verified B5.5 receipts before constructing the candidate graph.
- `orchestration::collect_normalized_batch_with_identity(invocations, limits,
  authority, cancel)`: preflights **all** exact source grants and run
  descriptors before executing the first collector, and delegates to the
  authenticated batch normalizer.

The ordinary non-keyed `normalize_batch` and `collect_normalized_batch`
functions remain unchanged in behavior; they do not accept keyed X.509 hints.

The batch matcher uses real canonical asset IDs and independently verified
direct EvidenceIds from per-run normalization. It cannot build a relationship
from imported snapshots or unauthenticated HMAC-shaped strings. Duplicate
public certificates observed through PEM and DER or through the explicitly
granted Windows-store adapter become one certificate asset while preserving
distinct direct evidence and typed source coverage. The inferred evidence
references an actual child observation's run and authorized source, not a
fabricated batch run.

The candidate coverage marker is
`x509:issuer-candidate:v1:batch`. Partial/failed source coverage, a missing
or unsupported identity, skipped cycle, ambiguous fanout or a resource cap
results in `Partial` rather than a statement that no issuer exists.

### Out of scope

This batch join is not temporal path validation, trust-anchor endorsement,
signature verification or revocation checking. It also does not authorize
federating previously materialized/imported snapshots: an attacker who can
rewrite a snapshot digest cannot impersonate a host-owned HMAC authority.

## Review hardening and bounded snapshot growth

B5.6 reconciles identical certificate `event_id` replays within each run before
charging candidate index quotas. The original outcome is retained unchanged for
the existing normalizer, which rejects duplicate IDs carrying divergent content.

Derived candidate coverage cannot overwrite any existing coverage key or a
requested/typed source label, even if that source emitted no observations. Such
a collision fails closed rather than changing the reported inspection outcome.

The matcher preflights the canonical semantic JSON size of the base inventory,
including a worst-case candidate-stage coverage marker. Each proposed inferred
evidence and relationship entry consumes a conservative additive serialization
budget (keys, values, separators). Once the remaining snapshot-byte headroom
cannot accommodate an edge, further inference is bounded and candidate coverage
becomes `Partial`, retaining the original asset and direct-source evidence.
If even the base inventory plus its coverage marker exceeds a configured byte
ceiling, normal validation reports `LimitExceeded`; it does not fabricate a
successful or exhaustive inventory.

The source grant boundary and the HMAC authority are unchanged. No trust-chain
path search, certificate signature validation or automatic CA/store discovery
is performed by the candidate matcher.
